# ROADMAP – zurückgestellte Punkte, Schulden, Ideen

> Laufend gepflegt (siehe CLAUDE.md Abschnitt 8). Nichts hier ist vergessen – nur bewusst verschoben.

## Zurückgestellte Features

- **Multi-Device-Support:** v1 startet mit einem Gerät pro Account; Geräte-Verknüpfung wie bei Signal/WhatsApp später (CLAUDE.md Abschnitt 6)
- **Serverseitige Volltextsuche:** wegen E2EE prinzipbedingt nicht möglich; v1 sucht nur clientseitig in entschlüsselten Nachrichten
- **Voice/Video-E2EE:** Voice läuft zunächst nur transportverschlüsselt (TLS/DTLS-SRTP über SFU), echte E2EE (z. B. Insertable Streams) später
- **Native Clients / Desktop-App:** perspektivisch, u. a. wegen des Web-E2EE-Trade-offs (s. u.)

## Offene Sicherheits-Trade-offs

- **Web-E2EE-Grundproblem:** Der Server liefert den Krypto-Code als JavaScript aus; ein kompromittierter Server könnte manipulierten Code ausliefern. Milderungen später: Subresource Integrity, signierte Builds, native Clients (CLAUDE.md Abschnitt 6)
- **Trust on first use (Phase 6):** Clients vertrauen den Schlüsselbündeln, die der Server ausliefert – ein kompromittierter Server könnte Bundles austauschen (MITM). Milderung später: Fingerprint-/“Safety-Number“-Verifikation in der UI, wie bei Signal
- **X3DH ohne One-Time-Prekeys (Phase 6):** bewusst der in der Signal-Spezifikation dokumentierte Fallback-Modus; OPKs (bessere Forward Secrecy für die ERSTE Nachricht einer Session) später ergänzen (Server-Endpunkt zum Nachfüllen + Verbrauch beim Abruf)
- **Sender-Key-Rotation ist Best-Effort (Phase 6):** Rotiert wird, wenn der Client ein `SERVER_MEMBER_REMOVE` live sieht. Wer beim Austritt offline war, rotiert nicht (der Ausgetretene erhält zwar weder Events noch History vom Server, könnte aber bei einem späteren DB-Leak mit seinem alten Schlüssel mitlesen). Fix-Idee: Mitglieder-Abgleich beim Reconnect oder serverseitiges Rotations-Signal
- **Sender-Keys gehen an ALLE Server-Mitglieder,** auch ohne ViewChannels (Ciphertext-Zugriff sperrt der Server). Solange Rechte serverweit gelten unkritisch – bei Kanal-Overwrites (s. u.) neu bewerten
- **Schlüsselmaterial liegt unverschlüsselt in IndexedDB** (wie z. B. bei Signal Desktop auf der Platte). Passphrase-Schutz/Key-Backup wäre ein eigenes Feature – zusammen mit Multi-Device betrachten
- **Zitat-Vorschauen sind absenderkontrolliert (Phase 9):** Die in `replyTo` eingebettete Vorschau (Text + zugeschriebener Absender) wird beim Empfänger angezeigt, ohne sie gegen die Originalnachricht zu prüfen – ein manipulierter Client kann also ein „Zitat“ fälschen, das so nie geschrieben wurde (gleiche Eigenschaft wie bei Signal-Zitaten). Milderung später: Vorschau gegen die lokal geladene Originalnachricht abgleichen und bei Abweichung markieren
- **DM-E2EE nutzt den Sender-Key-Ratchet, nicht das reine Double Ratchet (Phase 7):** CLAUDE.md §6 sah für 1:1-Chats ein Double-Ratchet-Protokoll pro Nachricht vor. Umgesetzt sind DMs stattdessen wie Kanäle (Sender-Key-Kette pro Teilnehmer, verteilt über die X3DH+Double-Ratchet-Sessions). Grund: Der Client speichert Klartexte bewusst NIE lokal – History muss nach jedem Reload aus dem Server-Ciphertext neu entschlüsselbar sein, was mit einem reinen Double Ratchet (Zustand wandert unumkehrbar vorwärts) nicht geht. Die Kette liefert weiterhin einen neuen symmetrischen Schlüssel pro Nachricht (Forward Secrecy über den gespeicherten frühesten Stand hinaus allerdings nicht) und kein per-Nachricht-DH (schwächere Post-Compromise-Security als echtes Double Ratchet). Echtes Double Ratchet für DMs wird sinnvoll, sobald ein lokaler Nachrichtenspeicher existiert (zusammen mit Multi-Device betrachten)
- Dev-Standardpasswörter in `docker-compose.yml`-Defaults (`parley_dev_password`) – nur für lokale Entwicklung; vor jedem echten Deployment durch Secrets ersetzen

## Technische Schulden / Vereinfachungen

- `@parley/shared` wird als CommonJS gebaut; der Web-Client umgeht das per Vite-Alias direkt auf die TS-Quelle (Rollup kann CJS-Enum-Re-Exports nicht statisch auflösen). Falls das später stört: Dual-Build (ESM+CJS)
- npm 10.9.8 gebündelt mit Node 22 – Update auf npm 11 optional
- ~~Docker-Compose-Verifikation~~ ✓ nachgeholt (05.07.2026), ~~Vitest-Setup~~ ✓ mit Phase 1 erledigt
- **Presence-Edge-Case:** Stürzt eine Gateway-Instanz hart ab, wird kein `PRESENCE_UPDATE offline` publiziert – der Redis-TTL (60 s) räumt den Zähler auf und `filterOnline` entfernt die Hash-Leiche lazy (Phase 14, im geprüften Sichtbarkeitskreis), aber bereits verbundene Clients sehen den Nutzer bis zum nächsten READY-Snapshot als online. Fix-Idee: Redis-Keyspace-Notifications oder periodischer Abgleich
- ~~**Presence-Snapshot skaliert linear**~~ ✓ mit Phase 14 erledigt: `getOnlineUsers()` (HGETALL über ALLE Online-Nutzer + Filter) ist entfernt; alle Pfade (READY-Snapshot, Server-Beitritt, neue Freundschaft) nutzen jetzt `PresenceService.filterOnline(candidateIds)` – O(Sichtbarkeitskreis) statt O(alle Online). Leichen im Presence-Hash werden dabei im geprüften Kreis lazy aufgeräumt (übernahm vorher `getOnlineUsers`)
- **Stale Presence-Einträge im Client:** Schrumpft der Sichtbarkeitskreis (Entfreunden, Server-Austritt), bleibt der Nutzer bis zum nächsten Reconnect im `onlineUsers`-Store des Clients (keine UI zeigt ihn an, aber der Eintrag lebt). Fix-Idee: gezieltes PRESENCE_REMOVE-Event oder Abgleich bei FRIENDS_UPDATE/SERVER_MEMBER_REMOVE
- ~~**`trust proxy`** nicht gesetzt~~ ✓ mit Phase 14 erledigt: über `TRUST_PROXY` in `.env` konfigurierbar (Hop-Zahl, z. B. `1`, oder ein von Express akzeptierter Ausdruck); leer im Dev ohne Proxy. Gesetzt nimmt Express `req.ip` aus X-Forwarded-For, damit das Rate-Limit pro echter Client-IP greift statt alle Nutzer gemeinsam unter der Proxy-IP zu drosseln
- **Dev-Infra ohne Docker:** Auf Maschinen ohne Docker Desktop laufen PostgreSQL/Redis/MinIO portabel (`scripts/dev-infra.ps1`); Redis ist dort ein 5.0-Windows-Port (tporadowski) – für die genutzten Kommandos (INCR/EXPIRE/Pub-Sub) ausreichend, aber kein 1:1-Ersatz für Redis 7 aus docker-compose
- **Sender-Key-Verteilung skaliert linear (Phase 6):** Beim Senden wird pro Mitglied das Schlüsselbündel geprüft (60-s-Cache) und bei Bedarf ein Umschlag verschickt – bei sehr großen Servern viele Requests. Später: `DEVICE_KEYS_CHANGED`-Gateway-Event statt Polling, Umschläge bündeln
- ~~Umschläge an beliebige Nutzer~~ ✓ mit Phase 7 erledigt: `POST /api/envelopes` UND `GET /users/:id/keys` verlangen jetzt den Sichtbarkeitskreis (Freunde, gemeinsame Server, bestehende DMs); 404 statt 403 gegen Nutzer-Enumeration
- **Skipped-Message-Keys im Double Ratchet** werden pro Kettenwechsel begrenzt (MAX_SKIP), aber nie global aufgeräumt – bei sehr langlebigen Sessions irgendwann beschneiden (Signal löscht nach Zeit/Anzahl)
- **E2EE-Testnutzer:** Die Verifikationsläufe von Phase 6 haben `charlie_…`-Wegwerf-Nutzer in der Dev-DB hinterlassen (Testserver wurden gelöscht; einen User-Lösch-Endpunkt gibt es noch nicht – kommt spätestens mit dem DSGVO-Löschkonzept). Phase 8 kam mit `p8…`-Nutzern dazu; Phase 9 hat einen `Phase9 <timestamp>`-Testserver in der (portablen) Dev-DB hinterlassen
- **Reaktions-Events sind normale Nachrichten (Phase 9, bewusste Entscheidung):** Der Server kann sie prinzipbedingt nicht von Text unterscheiden – dadurch (a) zählen sie gegen dasselbe Rate-Limit wie Nachrichten (30/30 s, exzessives Emoji-Toggeln drosselt also auch das Schreiben), (b) können History-Seiten (50er) überwiegend aus Reaktions-Events bestehen und der sichtbare Verlauf einer Seite entsprechend kurz ausfallen, (c) erscheinen NICHT entschlüsselbare Reaktions-Events (z. B. von vor dem Beitritt) als 🔒-Platzhalterzeile, weil der Client erst nach dem Entschlüsseln weiß, dass es keine Textnachricht war
- ~~**Erwähnungs-Benachrichtigung nennt fremde Server nur generisch (Phase 9)**~~ ✓ mit Phase 15 erledigt: `MESSAGE_CREATE` trägt bei Server-Kanälen jetzt `context` (Kanal- + Servername – Server-Metadaten, kein E2EE-Inhalt); der Client merkt sich die Labels und die Notification nennt Kanal und Server auch für nicht ausgewählte Server
- **Anhänge: kein Speicher-Kontingent (Phase 8):** Pro Nutzer greifen nur das Rate-Limit (30 Uploads/min), das 10-MiB-Limit und der Aufräum-Job für nie gebundene Uploads (Frist 6 h, läuft beim Start und stündlich). Ein echtes Quota pro Nutzer/Server fehlt – vor echtem Mehrbenutzer-Betrieb nachziehen
- **Anhang-Upload puffert im RAM (Phase 8):** Der Blob (max. 10 MiB) läuft komplett durch die API (`express.raw`-Buffer). Bei Skalierung auf presigned URLs umstellen (Client lädt direkt zu MinIO hoch/herunter, API vergibt nur noch signierte Links) – spart API-RAM und -Bandbreite
- **MinIO ohne TLS im Dev** (`MINIO_USE_SSL=false`): vor einem echten Deployment aktivieren bzw. die Verbindung am Reverse-Proxy terminieren
- **Voice-Roster in Postgres (Phase 10 → 14):** `VoiceSession` liegt weiterhin in der DB (wie im CLAUDE.md-Datenmodell), obwohl der Zustand ephemer ist. ~~Beim API-Boot werden ALLE Sessions gelöscht~~ ✓ mit Phase 14 ersetzt durch einen **Liveness-Abgleich**: der SFU setzt pro verbundenem Peer `voice:peer:{userId}` (Wert = channelId, TTL 30 s, 10-s-Heartbeat); die API entfernt beim Boot UND alle 30 s Sessions ohne lebenden Liveness-Key (mit 30-s-Beitritts-Karenz), statt destruktiv alle zu löschen → **multi-instanz-fest** (ein Neustart reißt keine Sessions noch verbundener Nutzer anderer Instanzen mehr mit; `voice:disconnect` bleibt der schnelle Pfad, der Abgleich ist die Absicherung gegen verpasste Signale/SFU-Absturz). **Offen:** der Roster selbst könnte nach Redis wandern (dann kein Postgres-Roundtrip pro Roster-Änderung) – der aktuelle Ansatz ist für moderate Last ausreichend
- **Voice-SFU: ein mediasoup-Worker (Phase 10):** ein Worker, ein Router pro Sprachkanal. Für hohe Last mehrere Worker + Router-Piping – Phase 14 hat die Roster-**Korrektheit** für Multi-Instanz gehärtet (Liveness-Abgleich, s. o.), aber NICHT die Medien-Kapazität eines einzelnen SFU erhöht; mehrere Worker bleiben offen. `MEDIASOUP_ANNOUNCED_IP` muss für LAN/Server gesetzt werden, sonst finden Clients außerhalb `localhost` den SFU nicht
- **Phase 14 – offene Skalierungspunkte (bewusst zurückgestellt):** Die Phase hat die Korrektheit horizontaler Skalierung gehärtet (gezielte Presence-Abfragen, multi-instanz-fester Voice-Roster, `trust proxy`) und die DB-Indizes geprüft (Hot-Paths sind seit den früheren Phasen abgedeckt: Message `[channelId,createdAt]`, AuditLog `[serverId,createdAt]`, Membership/Channel/Role/Invite/Push je `serverId`/`userId`, KeyEnvelope `[toUserId,createdAt]`, Voice `channelId`/unique `userId` – kein neuer Index nötig). **Noch offen und einer eigenen Infra-Session vorbehalten:** echte **Lasttests** (brauchen ein deployed Multi-Instanz-Setup, lokal nicht aussagekräftig), **presigned Upload-URLs** (s. o., Anhang-RAM-Puffer), **Sender-Key-Verteilung entkoppeln** (`DEVICE_KEYS_CHANGED` statt Polling, s. o.), Voice-Roster nach Redis (s. o.) und eine Message-Queue (z. B. NATS) für sehr große Last (Redis-Pub/Sub trägt den aktuellen Umfang)
- ~~**Web-Bundle wächst durch mediasoup-client (Phase 10)**~~ ✓ mit Phase 15 erledigt: `store/voice.ts` importiert `VoiceClient` nur noch als Typ und lädt das Voice-Modul per dynamischem `import('../lib/voice')` erst beim ersten Beitritt (parallel zum Join-Request). Rollup legt mediasoup-client dadurch in einen eigenen Chunk – das Initial-Bundle sank von 975 KB auf 736 KB (gzip 285 → 242 KB), der Voice-Chunk (239 KB / 43 KB gzip) lädt nur bei Bedarf. Verifiziert im Browser (vor Beitritt nicht geladen, nach Beitritt nachgeladen, Voice verbindet, Konsole sauber)
- **Reconnect-Rejoin setzt Mute/Deafen kurz zurück (Phase 10):** Nach einem Gateway-Reconnect registriert der Client die Voice-Session neu (`POST …/join`, das serverseitig auf ungemutet setzt) und zieht den lokalen Mute-/Deafen-Zustand direkt per PATCH nach – für andere kann der Zustand einen Moment falsch aussehen (Phase 11: gilt genauso für Kamera/Screen – `reregisterAfterReconnect` zieht alle vier Booleans nach)
- **Video ohne Simulcast/adaptive Bitrate (Phase 11):** Kamera und Bildschirm werden mit EINER festen Encoding-Schicht gesendet (`maxBitrate` 600 kbit/s bzw. 2,5 Mbit/s). Kein Simulcast (mehrere Auflösungen), keine bandbreitenabhängige Layer-Wahl pro Empfänger – bei vielen Teilnehmern/schwacher Leitung nachrüsten (mediasoup unterstützt Simulcast, `encodings` erweitern + serverseitige Layer-Steuerung)
- **Screen-Share ohne Ton (Phase 11):** `getDisplayMedia` wird mit `audio: false` aufgerufen – geteilter Tab-/System-Ton wird nicht übertragen. Später optional die Screen-Audiospur als zweiten Producer (`source: 'screen'`, kind audio) mitschicken
- **Video-Bühne ist ein simples Raster (Phase 11):** `VoiceStage` legt alle Kacheln in ein 1–3-Spalten-Grid. Kein aktiver-Sprecher-Fokus, kein Anpinnen/Vollbild einer Kachel, keine getrennte Darstellung von Screen-Share (groß) vs. Kameras (klein) – UI-Feinschliff (Phase 15)
- **Kamera/Screen-Indikator ist client-gemeldet (Phase 11):** `cameraOn`/`screenOn` im Roster kommen wie Mute per PATCH vom Client, nicht vom SFU. Ein manipulierter Client könnte den kleinen Indikator (📹/🖥️) falsch setzen – die tatsächlich gerenderte Video-Kachel stammt dagegen aus der SFU-Producer-Liste und lässt sich so nicht fälschen. Unkritisch (rein kosmetisch), zusammen mit serverseitiger Voice-Wahrheit betrachten
- **Bann nur gegen Mitglieder, kein Message-Pruning (Phase 13):** Gebannt werden kann nur ein aktuelles Mitglied (kein „Bann per User-ID“ für Nie-Mitglieder wie bei Discord). Beim Bann werden keine bisherigen Nachrichten gelöscht (Discord bietet „Nachrichten der letzten X Stunden löschen“ an) – bei Bedarf als Option nachrüsten
- **Auszeit läuft passiv ab (Phase 13, UI-Teil ✓ mit Phase 15):** `Membership.timeoutUntil` wird nicht proaktiv geleert; die Durchsetzung vergleicht bei jedem Senden/Voice-Beitritt gegen `now`. Ein abgelaufener Zeitstempel bleibt in der DB (harmlos). Das ⏳ im Mitglieder-Panel verschwindet seit Phase 15 per client-seitigem Timer beim Ablauf (ohne Reload); ein serverseitiges `SERVER_MEMBER_UPDATE` zum Ablaufzeitpunkt gibt es weiterhin nicht (andere Clients ohne offenes Panel brauchen es nicht – der Timer läuft überall lokal)
- **Audit-Log ohne Pagination/Live-Feed (Phase 13):** `GET /api/servers/:id/audit-log` liefert die neuesten 100 Einträge, neueste zuerst; keine Cursor-Pagination und kein Live-Event (der Dialog lädt beim Öffnen). Für große Server nachziehen. Protokolliert werden Kick/Bann/Entbann/Timeout/Timeout-Ende/Mod-Nachrichtenlöschung/Voice-Trennen – Rollen-/Kanal-/Server-Änderungen (Phase 3/5) sind bewusst NICHT im Audit-Log (später ergänzbar)
- **Keine „Du wurdest gebannt/gekickt“-Rückmeldung (Phase 13):** Der Betroffene erhält nur `SERVER_MEMBER_REMOVE` (der Server verschwindet wie beim Verlassen) – ohne Grund/Hinweis. Ein eigenes Event mit Grund wäre nutzerfreundlicher

## Ideen aus der Entwicklung

- **Ownership-Übergabe:** Der Owner kann seinen Server aktuell nur löschen, nicht übergeben; „Server verlassen“ ist für Owner gesperrt. Übergabe-Flow sinnvoll ab Phase 13 (Moderation)
- **Rollen-Hierarchie – teils erledigt (Phase 5 → 13):** Die **Moderation** (Phase 13) setzt jetzt eine Hierarchie durch: Kick/Bann/Timeout/Voice-Trennen gehen nur gegen Mitglieder mit STRIKT niedrigerem Rang (höchste Rollen-Position; Owner = ∞), nie gegen den Owner oder sich selbst (`PermissionsService.getMemberRank`). **Noch offen:** Die **Rollen-Verwaltung** kennt weiter keine Hierarchie – jeder mit ManageRoles kann jede Rolle bearbeiten/zuweisen, auch sich selbst höhere Rechte geben (inkl. Administrator). Discord beschränkt das auf „nur Rollen unterhalb der eigenen“. Vor echtem Mehrbenutzer-Betrieb nachziehen (`position` existiert)
- **Kanal-spezifische Berechtigungen (Overwrites)** und private Kanäle (`isPrivate` ist bislang nur ein Flag ohne Wirkung) – späteres Feature
- **Gateway-Events vs. ViewChannels:** `MESSAGE_CREATE` geht seit Phase 5 nur an Mitglieder mit ViewChannels (`getMemberIdsWithPermission`); Struktur-Events (`CHANNEL_*`, `ROLE_*`, `SERVER_MEMBER_*`) gehen weiterhin an alle Mitglieder – unkritisch, solange Rechte nur serverweit gelten, bei Kanal-Overwrites neu bewerten
- ~~**UI-Feinschliff Rollen:** Rollenfarben wirken bisher nur auf Badges~~ ✓ mit Phase 15 erledigt: Farb-Palette im Rollen-Dialog (`color` per PATCH, `null` entfernt, Standardrolle bleibt serverseitig farblos); die Farbe der höchsten farbigen Rolle färbt Namen im Mitglieder-Panel und Absendernamen im Chat
- ~~Beitritt per Server-ID~~ ✓ mit Phase 12 erledigt: Beitritt läuft nur noch über Invite-Codes (mit Ablauf/Limit); der offene `POST /servers/:id/join`-Endpunkt, die Store-Methode und der „ID kopieren“-Button sind entfernt
- ~~**Nachrichten bearbeiten/löschen**~~ ✓ mit Phase 13 erledigt: `PATCH`/`DELETE /api/channels/:id/messages/:messageId` (Autor bearbeitet/löscht eigene; ManageMessages löscht fremde in Server-Kanälen, mit Audit-Log-Eintrag), Gateway `MESSAGE_UPDATE`/`MESSAGE_DELETE`, gebundene MinIO-Blobs werden beim Löschen mit entsorgt (`MessagesService.removeBlobs`). **Weiterhin offen:** Reaktions-Events auf gelöschte Nachrichten und Antworten (`replyTo`) auf gelöschte Nachrichten bleiben als verwaiste Zeilen/Zitate zurück (Phase 9); die **Bearbeitung ändert nur den Text**, nicht die Anhänge einer Nachricht
- **Erwähnungen sind Namens-Matching, keine ID-Referenzen (Phase 9):** `@name` wird nach dem Entschlüsseln per Textsuche über die bekannten Benutzernamen erkannt. Benennt sich ein Nutzer um, verlieren alte Erwähnungen ihr Highlight; Namens-Kollisionen über Server-Grenzen sind möglich. Discord löst das mit ID-Tokens (`<@userId>`) im Text – wäre auch hier E2EE-kompatibel, braucht aber einen Erwähnungs-Picker in der Eingabezeile
- **Kein eigenes AddReactions-Recht (Phase 9):** Reaktionen sind technisch Nachrichten und hängen daher am SendMessages-Bit; ein separates Berechtigungs-Bit (wie bei Discord) wäre nur UI-seitig durchsetzbar, weil der Server Reaktionen nicht erkennen kann – bewusst weggelassen
- ~~**Zitat-Klick lädt das Original nicht nach (Phase 9)**~~ ✓ mit Phase 15 erledigt: „Zum Original springen“ lädt History rückwärts nach (Deckel 10 Seiten à 50 – ein gefälschtes/uraltes Zitat kann nicht den kompletten Verlauf durchladen), scrollt hin und lässt die Nachricht aufleuchten; darüber hinaus klare Fehlermeldung
- ~~**DM-Ungelesen-Anzeige fehlt (Phase 7)**~~ ✓ mit Phase 15 erledigt: Live eingetroffene fremde DM-Nachrichten zählen pro Kanal als ungelesen (erst nach dem Entschlüsseln – Reaktions-Events zählen nicht), Badge in der DM-Liste + aufsummiert auf dem Zuhause-Button; Öffnen der DM leert den Zähler. Nur im Speicher – was während einer Trennung/geschlossenem Tab ankommt, wird nicht nachträglich markiert (ein persistenter Gelesen-Stand pro Kanal wäre ein Folge-Feature)
- **Blockieren lässt die DM-History lesbar (Phase 7, bewusste Entscheidung):** Eine Blockierung sperrt nur das SENDEN in beide Richtungen; bereits ausgetauschte Nachrichten bleiben für beide lesbar (wie bei Discord). Gruppen-DMs (mehr als zwei Teilnehmer) sind vorbereitet (`DmMember` ist n:m), aber bewusst nicht umgesetzt
- ~~Presence global statt gescoped~~ ✓ mit Phase 7 erledigt: READY-Snapshot und PRESENCE_UPDATE gehen nur noch an den Sichtbarkeitskreis (Freunde, gemeinsame Server, DM-Partner); PRESENCE_SYNC liefert additiv nach, wenn der Kreis wächst (Server-Beitritt, neue Freundschaft)
- **Keine eigenen Voice-Rechte (Phase 10):** Beitritt zu Sprachkanälen hängt am `ViewChannels`-Bit. Discord hat eigene `Connect`/`Speak`/`Video`-Rechte – als eigene Berechtigungs-Bits nachrüstbar (das Bitfield aus Phase 5 hat Platz), sinnvoll zusammen mit Moderation (Phase 13)
- ~~**Voice-Moderation fehlt (Phase 10 → 13)**~~ ✓ mit Phase 13 erledigt: `POST /api/servers/:id/members/:userId/voice-disconnect` (Recht: ModerateMembers, Hierarchie-geschützt) trennt ein Mitglied aus dem Sprachkanal – die API publiziert `voice:force-disconnect`, der SFU schließt die betroffene Medien-WS (Close-Code 4006) und räumt den Roster. Timeout trennt zusätzlich automatisch aus dem Voice und sperrt den Voice-Beitritt. **Noch offen:** serverseitiges Force-Mute/Move (nur Trennen), und die Indikatoren im Roster bleiben client-gemeldet (s. o.)
- **Keine Sprech-Anzeige (Phase 10):** Es gibt keinen „spricht gerade"-Indikator (Audio-Pegel). Über mediasoup-`AudioLevelObserver` (serverseitig) oder client-seitige WebAudio-Pegelmessung nachrüstbar – Feinschliff
- **Voice: keine Gruppen-DM-/DM-Sprachanrufe (Phase 10):** Sprachchat gibt es nur in Server-Sprachkanälen, nicht in DMs. 1:1-/Gruppen-DM-Calls wären ein Folge-Feature (Signaling-Ebene ist kanalbasiert und ließe sich auf DM-Kanäle erweitern)
- **Push nur bei Offline & pro Nutzer, nicht pro Gerät (Phase 12):** Web-Push geht nur an Nutzer OHNE aktive Gateway-Verbindung (online → In-App/Notification-API aus Phase 9). Hat jemand ein Gerät offen und ein zweites geschlossen, bekommt das geschlossene keinen Push, weil Presence pro Nutzer (nicht pro Gerät) zählt. Sauber erst mit echtem Multi-Device (Presence/Push pro Gerät)
- **Erwähnungs-Push ist ein Client-Hinweis (Phase 12):** Da der Server Erwähnungen im E2EE-Ciphertext nicht erkennt, meldet der SENDENDE Client per `POST /channels/:id/notify-mentions`, wen er erwähnt hat. Der Server prüft die Sende-Berechtigung, filtert auf echte Kanal-Mitglieder und pusht die offline unter ihnen. Ein manipulierter Client könnte damit beliebige (berechtigte) Mitglieder „erwähnen" und pushen – gedeckelt durch das Send-Rate-Limit und Offline-Only. Eigenes Missbrauchslimit ggf. nachziehen
- **Push-Inhalte sind Metadaten (Phase 12):** Der Push-Body enthält keinen Nachrichtentext (E2EE), aber Absender-Username und Kanalname als Metadaten – der Server kennt diese ohnehin. Für strengere Metadaten-Sparsamkeit ließe sich der Push noch generischer halten („Neue Aktivität")
- **Kein periodisches Aufräumen toter Push-Subscriptions (Phase 12):** Abgelaufene Subscriptions werden nur beim Sende-Versuch (404/410 → löschen) entfernt. Subscriptions von Nutzern, die nie wieder gepusht werden, bleiben liegen – gelegentlicher Cleanup-Job wäre sinnvoll. Unbegrenztes Wachstum verhindert seit dem Review ein Deckel (max. 10 pro Nutzer, älteste fliegen raus)
- **Push-Endpoint-Validierung ist https-only, keine Zielliste (Phase 12, Review):** `POST /push/subscribe` verlangt eine https-URL (+ Längenlimits) – das blockiert den Missbrauch der API als Relay gegen interne HTTP-Ziele; interne https-Ziele scheitern zusätzlich an der TLS-Zertifikatsprüfung von `web-push`. `require_tld` ist für lokale Tests aus; eine Allowlist bekannter Push-Dienste (FCM/Mozilla/APNs-Web) wäre die strengste Ausbaustufe
- **CreateInvite ist nicht in der Standardrolle (Phase 12, bewusste Entscheidung):** Frische Server erlauben Einladungen nur dem Owner (Administrator) bzw. Rollen, denen jemand das neue CreateInvite-Bit gibt – restriktiver als Discords @everyone-Default. Bei Bedarf pro Server über die Rollen-UI änderbar; als Produkt-Default neu bewerten, wenn Onboarding wichtiger wird als Kontrolle
- **Web-Push braucht HTTPS + echten Push-Dienst (Phase 12):** `web-push` sendet immer über TLS an den Browser-Push-Dienst (FCM/Mozilla/…); im lokalen Dev ohne HTTPS/echten Dienst ist die tatsächliche Zustellung nur mit einem HTTPS-Endpoint testbar. VAPID-Schlüssel liegen in `.env`; fehlen sie, ist Push sauber deaktiviert. Vor echtem Betrieb VAPID-Keys pro Umgebung erzeugen
- **SPA-Deep-Link `/invite/<code>` braucht History-Fallback (Phase 12):** Im Dev übernimmt das der Vite-Server; ein produktiver Static-Host/Reverse-Proxy muss unbekannte Pfade auf `index.html` mappen, sonst öffnet ein direkt aufgerufener Einladungslink 404
